# Nila Shoshsho backend roadmap

The Node account service owns identities, profiles, staff reviews, private file references, notifications, transport and telephone callbacks. The Flask advice service verifies the same bearer token and checks the active account before using weather, market and AI providers. Neon stores account data. The current API contract is [openapi.json](openapi.json). [RELEASE.md](RELEASE.md) defines the checks for putting the existing product on a public host.

This roadmap reconciles [BACKEND_ELEVATION_PLAN.md](../BACKEND_ELEVATION_PLAN.md), [AGENTIC_AI_STRATEGY_2027.md](../AGENTIC_AI_STRATEGY_2027.md) and all six files in [guide](../guide). The two numbered plans describe essentially the same feature sequence. The longer version also identifies the historical limiter, image validation and destructive setup defects. The guide's agent rules and testing runbook set the acceptance standard. The older contract is a design proposal. Verify each method against the service and OpenAPI before wiring a client. For example, profile and logistics transitions use PUT, feature search uses GET, and scheme search uses POST.

| Sequence | Product work | What qualifies it for release |
| --- | --- | --- |
| 1. Existing backend | Run both APIs on an approved staging host. Verify managed sign-in, private uploads, staff-approved transport, enabled advice, voice and outage behavior. Keep restricted feeds and the telephone pilot behind their access gates. | Shared rate limiting across workers, HTTPS and browser origins, monitored host load, a restore rehearsal, and review of consequential agricultural advice for the supported regions. |
| 2. Traceable AI | Keep the useful elevation ideas: version model prompts and input contracts, validate outputs and record decisions. The first slice is structured Gemini crop observations, request-correlated outcome logs, and explicit transport permissions at the router. | Verify every event with synthetic traffic and a privacy review. Production traces should carry request ID, operation, provider and accepted/uncertain/failed outcome. For deeper reproducibility, use approved evidence references, prompt/model versions, restricted access and finite retention. Raw prompts, output, photos and farmer records stay outside routine logs. |
| 3. Grounded advice | Route supported intents to a small catalog of typed, read-only weather, market and agronomy functions. Preserve the text response for existing clients. For current facts, use the authoritative feed with location and timestamp and make an unavailable-data outcome explicit. | Evaluate in the chosen languages, including ambiguous questions and malicious instructions embedded in input or retrieved data. Each tool needs an authorization rule, input/output validation, a timeout and a call budget. Introduce a classifier only when representative tests show it improves routing. |
| 4. Markets and plots | Get authorized, usable historical mandi data first. Ingest data with complete market, variety, grade, unit and date keys. Ship owner-scoped saved plots before satellite monitoring. Evaluate satellite trends with plot boundaries, cloud masks, age and no-data handling. | Mandi forecasts need rolling backtests against last-price and seasonal baselines, measured errors and calibrated intervals for each released market and horizon. Fourteen days of data alone cannot support a launch decision. Satellite greenness is a vegetation signal. Validate local weather and agronomic rules before issuing any spray-window guidance. |
| 5. Proactive workflows | Start with opt-in notifications or an in-app draft suggestion. A farmer can review and explicitly confirm a transport job through the existing authorization boundary. Use reliable background leases, a fixed scope and an auditable decision trail. | Verify duplicate delivery and confirmation, stale drafts, concurrent writes, permission changes, crash recovery and spend limits. Require clear approval for every external transaction. Additional agents or orchestration frameworks need a measured operational benefit. |
| 6. Provider expansions | Finish the Bolna pilot when a configured agent and consenting recipient are available. Evaluate BHASHINI recognition and synthesis separately before adding a fallback. Add DigiLocker, AgriStack, PMFBY and official IMD functions only against the approved scopes and feed contracts. | API Setu samples stay in test fixtures. Live government access requires approved onboarding, user consent, audience and replay checks where applicable, and documented withdrawal/deletion. Verify which policy events and reporting deadlines apply. A crop photo cannot authorize a claim, verify an identity or establish policy eligibility. |

The saved-plot API now implements the owner-scoped part of phase 4. Approximate centers are labeled as farmer-entered data. Satellite analysis begins once plot boundaries and verified observations are available.

The crop-photo model may abstain. Its score is a model signal, and verified regional guidance is required before offering actionable treatment or fertilizer rates. Structured output helps clients safely interpret the fields. It does not establish agronomic accuracy. The root plans' forecasts about industry adoption, the implied 2027 compliance deadline and the fixed dosage examples are unsuitable as release criteria. The engineering rule is to prove the actual behavior with evidence for the intended market.

Scope each release as a complete working slice. Keep the current Android, iOS and web/PWA clients on the documented API contract. Record supplier access, passing tests, unresolved risks and actual recovery evidence in [the release runbook](RELEASE.md).
